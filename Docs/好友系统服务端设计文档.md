# 好友系统服务端设计文档

> 范围：86JP 服务端 `Server/DfoServer` 好友系统的完整协议流、实现细则与信令权威来源。
> 面向：后续接手本模块的开发人员 / 需要理解客户端-服务端好友交互的人。
> 日期：2026-08-22（好友系统全量打通：单向化 + 添加 + 删除 + 上下线 + 状态变更推送）

---

## 1. 概述

### 1.1 功能范围

好友系统当前已实现：

| 能力 | 入口 | 状态 |
|---|---|---|
| 单向好友关系存储 | `united_friend_relations` 表 | ✅ 生产 |
| 添加好友 | `0x0122 ADD_UNITED_SERVER_FRIEND` | ✅ 生产 |
| 删除好友 | `0x0123 DELETE_UNITED_SERVER_FRIEND` | ✅ 生产 |
| 好友列表下发/刷新 | `0x0111 UNITED_SERVER_FRIEND_INFO` | ✅ 生产 |
| 上线/下线推送 | `0x0112 INOUT_UNITED_SERVER_FRIEND` + `0x0002 USERINFO` + `0x0006 USER_LEAVE` | ✅ 生产 |
| 状态变更推送（在线/繁忙/PvP） | `0x0002 USERINFO` | ✅ 生产 |

### 1.2 核心语义（用户拍板）

1. **好友关系是单向的**：A 添加 B 只记 `A→B`，B 未必添加 A。`united_friend_relations` 表每行 `(owner_name, friend_name)` 只表示 a→b，加载时**不补反向边**。
2. **推送方向是"谁的面板显示谁"**：谁把 B 加为好友（`IsFriend(观察者, B)`），谁收到 B 的通知。A 删 B 后，B 的一切推送自动对 A 停止（门控自然断开）。
3. **绿/灰图标是场景实体驱动的**，不是好友树节点状态位。登录/上线推 USERINFO 注入实体 → 绿；登出推 USER_LEAVE 移除实体 → 灰。
   > ⚠️ **猜测声明**：用 USERINFO/0x0006 leave 实现图标转换是**服务端推断，非客户端反编译定论**。由此衍生：
   > - 城镇区域离开广播（`TownHandler.NotifyLeaveAsync`）对**好友抑制** leave 包——好友从玩家当前区域离开（返回选人/切区域/断线）时，不把该 leave 发给好友，避免其图标误转灰（只对非好友广播）。此抑制是上述猜测引发的修改。
   > - 若后续有明确的反编译行为推翻该机制，需复查本抑制并恢复对同区域所有玩家广播（§4.8 与本点一并复核）。
4. **场景实体只在同频道可见**；上下线聊天通知 `0x0112` 跨频道也推（无实体）。
5. **等级/职业刷新是事件驱动的**：升级/转职由【升级者主动推送】重推好友列表（§4.7），不做定期刷新——单进程内存实时，可即时推送，无延迟。

### 1.3 架构

- 无 DI 容器：`UnitedFriendSystem` 是静态单例，`lock(Sync)` 保护内存图。
- 持久化走 SQLite 表 `united_friend_relations`（见 §2.2），数据访问经 `UnitedFriendRepository`；
  表不存在时由 schema/迁移创建空表，与其它表项行为一致（无运行时隐式建表、无存量数据导入）。
- 所有发包走 `GamePacketEnvelopeBuilder.Build(cmd, type, body)` + `GamePacketWriter` 顺序写字段。
- 日志统一 `FileLogger.Log`（`[UnitedFriend]` / `[GameProtocol]` 前缀）。

## 2. 数据模型

### 2.1 内存结构

```csharp
Dictionary<string, HashSet<string>> Friends;   // a → {b1, b2, ...}，键区分大小写（与角色名一致）
```

- `GetFriends(name)`：name 的好友名列表（排序）。
- `IsFriend(a, b)`：a→b 是否存在（方向敏感）。
- `RecordFriendship(a, b)`：加 a→b 边（幂等）+ 持久化。
- `RemoveFriendship(a, b)`：删 a→b 边，空集清理 + 持久化，返回是否存在。

**运行期权威是内存图**：上线/下线/状态/列表刷新的全部查询（`IsFriend`/`GetFriends`）都只走内存
`Friends`（O(1) 哈希命中），数据库表只在启动加载、加边、删边时访问。这是单进程、好友关系全量常驻
内存的自然表达——不做"查表再缓存"的两级冷启动，省掉一次启动全表扫描后的内存与 IO 双重开销。

### 2.2 持久化 `united_friend_relations` 表

表结构与建表/迁移的落点：

```sql
CREATE TABLE IF NOT EXISTS united_friend_relations (
    owner_name  TEXT NOT NULL,                  -- a（添加者）
    friend_name TEXT NOT NULL,                  -- b（被添加者，单向 a→b）
    created_at  TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (owner_name, friend_name)        -- 唯一约束 + 正向查询索引
);
CREATE INDEX IF NOT EXISTS idx_united_friend_relations_friend
    ON united_friend_relations(friend_name);     -- 覆盖反向查询"谁把 X 加为好友"
```

- 建表：新库由 `item_schema.sql`（完整最终形态）创建；旧库由 `SqliteMigrations` **v57** 迁移创建空表。
  两处同步维护（CONTRIBUTING 硬性要求），与其它表项一致。`UnitedFriendRepository` 只做表 CRUD，
  **不运行时隐式建表**。（`Data/friends.txt` 仅本机验证用临时文件，不进 MR、无导入逻辑。）

**为什么用角色名做键（而非 `character_id` 外键）**——这是本表最重要的设计决定：

1. **联合服好友可能跨服**。客户端协议 ADD 携带 `targetUserID` 与名字，但本服 `characters` 表不含
   其它服的对方角色，`character_id` 没有跨服对应物；名字是协议里唯一稳定、跨服可比的标识。
2. **好友关系应存活于角色删除之后**。若加 `FOREIGN KEY ... ON DELETE CASCADE`，角色删除会连带清掉
   其好友边；而删除角色后玩家重练同名角色，好友关系应当还在。名字键天然满足这一点。
3. 名字键与协议载荷（`0x0111` entry、`0x0112` 通知都只带名字）同构，加载/回写零转换。

**为什么对齐大小写敏感**：`characters.name` 唯一索引为 BINARY（大小写敏感），`Abc` 与 `abc` 是两个
不同角色；好友键必须与之一致。若用 NOCASE/忽略大小写，两个不同角色会被当成同一好友（内存字典同键
互相污染好友列表、表 PK 冲突导致 INSERT 失败）。

**为什么 PK + 反向索引**：`PRIMARY KEY (owner_name, friend_name)` 同时充当唯一约束与正向查询索引
（`WHERE owner_name=?` 免排序命中）；`friend_name` 索引覆盖反向查询（`WHERE friend_name=?`，即
"谁把 X 加为好友"）。两张查询方向各 O(log n)，全表仅两列主数据 + 一个二级索引，行短、占用极小。

**写边/删边无显式事务**：单条 `INSERT OR IGNORE` / `DELETE` 由 SQLite 单语句原子执行；本表不属于
"多表组成的一次业务写入"（CONTRIBUTING 约定只在多表写同一事务时才需要显式事务）。

## 3. 协议总览

统一约定：

- **请求 ACK 复用请求 CMD type**：客户端发 `0x0122`/`0x0123`，服务端 ACK 也用同 type 回。
- **失败 ACK**：body = `[0x00, errorCode]`（2B）。客户端分派系统预读 flag：`0x00` → 错误弹窗（errorCode→文案）；非 0 → 成功。
- **成功 ACK（united-server 好友）**：body = `[0x01][3×int32]`（13B）。flag=0x01 → 余下 12B 走客户端 `0xD13F30` 解析。
- **命令 vs 通知**：请求/ACK 用 `cmd=0x01`；服务端主动通知（列表、实体、聊天）用 `cmd=0x00`。

| type | 名称 | 方向 | 用途 |
|---|---|---|---|
| `0x0002` | USERINFO | S→C | 实体注册/状态更新（subtype0 第 6 字节 = UserState） |
| `0x0006` | USER_LEAVE | S→C | 实体离开 |
| `0x0111` | UNITED_SERVER_FRIEND_INFO | S→C | 好友列表（subcmd=0 下发 / subcmd=2 删节点） |
| `0x0112` | INOUT_UNITED_SERVER_FRIEND | S→C | 好友上下线聊天通知 |
| `0x0122` | ADD_UNITED_SERVER_FRIEND | C→S / S→C | 添加好友请求 + ACK |
| `0x0123` | DELETE_UNITED_SERVER_FRIEND | C→S / S→C | 删除好友请求 + ACK |
| `0x0124` | PVP_BUDDY_CONN_LIST（=`REDEEM_LIST` 同值，复用） | S→C | **未实现**（仅设计，见 §8） |

## 4. 协议流详解

### 4.1 添加好友（C→S `0x0122`）

**请求 body**（实验确认）：

```
[targetUserID:u16][operation:u8][nameLen:u32][name:UTF-8]
例：添加 "abc" → FF-FF-01-03-00-00-00-61-62-63 (10B)
```

- `targetUserID=0xFFFF`：客户端本地缓存未命中，用名字查找。
- `operation=0x01`：添加。

**服务端流程**（`GameProtocolHandler.HandleAddUnitedServerFriend`）：

```
解析 body → 取 selfName
校验：
  目标名为空            → reject 0x15（该角色不存在）
  添加自己              → reject 0x01（静默，不弹）
  好友数≥100 且非好友   → reject 0x04（好友已满）
  目标角色不存在        → reject 0x15（该角色不存在）
通过 → RecordFriendship(self, target)
     → 成功 ACK 13B： [0x01][0x1BC6:i32][10:i32][2:i32]
     → NotifyFriendAddedAsync：被加好友在线且同频道 → 推其 USERINFO（图标绿）
     → SendFriendListAsync 全量刷新（subcmd=0 ×2）
```

**成功 ACK 13B 为何必须**：ADD/DELETE 共享统一响应分派——dispatcher 读 flag 非 0 后把余下 12B 交给 `0xD13F30` 解析 `3×int32`，`B-C>6` → 设 friend_manager flag=1（激活好友面板）。发不足 13B 会静默 ret，friend_manager 不激活。`fieldA=0x1BC6` 是有效范围下界（见 §7.4）。

**失败 ACK**：`[0x00, errorCode]`。errorCode 映射：

| errorCode | 客户端文案 |
|---|---|
| `0x04` | 好友已满，无法继续添加好友 |
| `0x07` | 普通频道限制（string 0x4B75） |
| `0x15` | 该角色不存在 |
| `0x01` / `0x0D` / `0x85` / 其他 | 静默（不弹） |

### 4.2 删除好友（C→S `0x0123`）

> ⚠️ **请求 body 与 ADD 不同构**：曾误按 ADD 格式解析导致客户端弹"列表不存在该角色"（血泪坑见 §6.3）。

**请求 body**：

```
[operation:u8][targetCharId:u32][name:UTF-8 到 body 尾]
例：删 characNo=4 "8888" → 01-04-00-00-00-38-38-38-38 (9B)
    删 characNo=3 "888"  → 01-03-00-00-00-38-38-38   (8B)
```

- **无** `[u16 targetUserID]` 前缀、**无** `[u32 nameLen]` 长度前缀；name 直达尾部。
- `targetCharId` 是被删好友的角色 ID（客户端本地节点查询命中）。

**服务端流程**（`GameProtocolHandler.HandleDeleteUnitedServerFriend`）：

```
解析 body：op=body[0], charId=u32(body,1), name=body[5..]
目标名兜底：body name 为空时按 charId 反查 _characterRepository.GetById().DisplayName
校验：
  目标无法解析 → reject 0x15
  自身无名     → reject 0x15
  非好友       → reject 0x05（防御性；"对方不在好友名单中"文案由客户端本地检查弹出，见 §6.3）
通过 → RemoveFriendship(self, target)
     → 成功 ACK 13B（与 ADD 同构）
     → SendFriendDeletedAsync（0x0111 subcmd=2 删节点）
     → SendFriendListAsync 全量刷新（subcmd=0 ×2）
```

### 4.3 好友列表（S→C `0x0111`）

**subcmd=0 下发**（`SendFriendListAsync`，登录/Add/Delete 后**连发两遍**）：

```
[subcmd:i32=0][count:i32=N]
+ N × [sR:u8=1][channel:u16][nameLen:u32][name:UTF-8]
      [Lv:u8][Job:i32][GrowType:u8][Y:u8=0][Z:i32=0]
```

- entry 里 `channel` 取真实频道（在线）或 0（离线）；Lv/Job/GrowType：在线取会话实时值，**离线按名字查 DB character 记录取真实值**（`SqliteCharacterRepository.GetByName`，`delete_flag=0`），查不到（异常/已删）才回退默认值 Lv=1/Job=0/GrowType=0。
- **大区 sR 恒为 1**：因本项目**不存在跨区系统**，好友系统实现作了简化——所有玩家大区固定为默认值 1（广东1），不读取/不维护真实大区字段。全链路（列表 entry、0x0112 聊天通知、subcmd=2 删节点）sR 均写死 1。客户端 `0x07`「只能添加相同大区的玩家」错误码在单区环境恒不触发（见 §7.5），无需实现跨区判断。
- **连发两遍原因**：第 1 遍建节点（`+0x5D=0` 被 UI 过滤隐藏），第 2 遍命中 `0x14E0730` 路径1 置 `+0x5D=1` 显示。只发一遍会不显示。

**subcmd=2 删节点**（`SendFriendDeletedAsync`，删除好友必须走）：

```
[subcmd:i32=2][count:u32=1][sR:u8=1][nameLen:u32][name:UTF-8]
```

- 客户端 `0x14DEF10` 从 RB 树**真正删除**该节点。
- **必须用 subcmd=2**：subcmd=0 只插入/更新节点、**不清陈旧节点**——删除后若只刷 subcmd=0，被删好友节点残留。

### 4.4 上线推送（登录 hook）

`CharacterSessionLifecycleCoordinator` → `NotifyPlayerEnteredGame(self, dir)`：

1. 给 self 下发好友列表（subcmd=0 ×2）。
2. 遍历在线会话 s，分两个方向：
   - **方向1（s 的面板显示 self）**：`IsFriend(otherName, selfName)` →
     - 推 `0x0112` 上线聊天（channel=真实频道 → "X 进入频道"，**跨频道也推**）；
     - 若同频道：推 `0x0002 USERINFO(self)` 注入实体 → 图标绿。
   - **方向2（self 的面板显示 s）**：`IsFriend(selfName, otherName)` 且同频道 →
     - 推 `0x0002 USERINFO(s)` → self 看好友绿。

**0x0112 body**（`BuildChatNoticeBody`）：

```
[channel:u16][sR:u8=1][nameLen:u32][name:UTF-8][oF:u8=0x00]
channel≠0 → "X 进入频道"；channel==0 → "X 退出频道"（客户端 0xD1A153 分支）
oF=0x00 → 不进黑名单（全程不用 oF≠0）
```

**USERINFO subtype0 body**（`UserInfoSubtype0Builder.BuildNotificationBody`）：

```
[subtype:u8=0][u16=1(大区)][u16 onlineUserId]
[Job:u8][GrowType:u8][Level:u8][PvpGrade:u8][PvpRatingGrade:u8][UserState:u8]   ← 第 6 字节 = UserState
[外观...]
```

### 4.5 下线推送（登出 hook）

`NotifyPlayerDisconnected(self, dir)`：遍历在线会话 s，`IsFriend(otherName, selfName)`（s 的面板显示 self）：

1. 推 `0x0112` 下线聊天（channel=0 → "X 退出频道"，跨频道也推）。
2. 若同频道：推 `0x0006 USER_LEAVE(uid)` 移除实体 → 图标灰。顺序：先 0x0112 后 0x0006。

**实体不会自动消失**（已反编译定论）→ 无需 MOVE 心跳，登录推一次即可；登出必须主动 USER_LEAVE 才会灰。

**与城镇区域广播的协作（§1.2 猜测声明）**：同区域广播 `TownHandler.NotifyLeaveAsync` 对好友**抑制** leave 包（只对非好友广播）。因此好友下线时，好友端置灰**只来自本 hook 的显式 USER_LEAVE**，不会因城镇区域广播重复触发；若好友仅是从当前区域离开（返回选人/切区域）而并未下线，图标也不因区域广播误灰。

### 4.6 状态变更推送（UserState）

`NotifyUserStateChanged(self, dir)`：self 的 UserState 变化后，向 `IsFriend(otherName, selfName)` **且同频道**的会话推 `0x0002 USERINFO`（subtype0，第 6 字节带新 UserState）→ 好友面板图标刷新。

**UserState 枚举**（客户端单点判断 `UserState==1 ? 繁忙 : 在线`）：

| 值 | 含义 | 触发场景 |
|---|---|---|
| `0x00` | 在线 | 城镇/回城/回选择/副本结算/死亡复活/组队解散/教程结束 |
| `0x01` | 繁忙 | 进副本选择/进副本 |
| `0x02` | PvP | PvP 建房/进房 |

**调用点全覆盖清单**：

| 场景 | 位置 | UserState |
|---|---|---|
| 城镇进入 | `TownHandler.cs` SetUserAreaCoreAsync | 0x00 |
| 回城 | `TownHandler.cs` ReturnSelfToTownAsync | 0x00 |
| 回选择 | `TownHandler.cs` ReturnSelectionToTownAsync | 0x00 |
| 副本结算回城 | `DungeonTownReturnCoordinator.cs` | 0x00 |
| 死亡复活回城 | `DungeonCombatHandler.cs` DEATH_RESPAWN | 0x00 |
| 组队解散/拉回 | `PartyHandler.cs` PullBackToTownWithinTransitionAsync | 0x00 |
| 新手教程结束 | `DungeonTutorialHandler.cs` | 0x00 |
| 进副本选择 | `DungeonEntryHandler.cs` | 0x01 |
| PvP 建房 | `PvpRoomHandler.cs` | 0x02 |
| PvP 进房 | `PvpRoomHandler.cs` | 0x02 |

### 4.7 等级/职业变更推送（事件驱动刷新）

升级/转职后由【升级者主动推送】：向把 self 加为好友的在线会话重推 `0x0111 subcmd=0` 全量好友列表，刷新列表中 self 的 Lv/Job/GrowType。

**设计决策：事件驱动，不做定期刷新。**

- **依据：服务端业务决策（非反编译结论）**。当前 86JP 服务端是**单进程**，好友关系图、在线会话、角色数据全在内存，升级判定点（`CharacterExperienceService`）与好友系统同进程 → 事件驱动**即时**推送，零延迟。
- 官方客户端"好友等级/职业常有延迟"的根源是**跨服架构 + 定期批量同步**（好友数据跨服汇总、定时下发），不是客户端问题。本项目无跨服层，不存在该限制——**不需要也不应该引入定期刷新**（定期刷新只会人为引入延迟）。

**推送对象与门控**：所有 `IsFriend(观察者, self)`（谁的面板显示 self）的在线会话。**不分频道**——等级/职业是好友【列表节点数据】，跨频道好友也在列表里显示（灰色图标但可见等级职业）；这与 USERINFO 场景实体（仅同频道，§1.2 第 4 点）和 §4.6 状态推送（同频道门控）不同。
> ⚠️ "跨频道好友可见等级/职业"是**推断**（依据节点数据模型 + 客户端跨频道也下发列表），**待实机验证**。

**机制**：

1. `NotifyFriendListInfoChanged(self, dir)`：遍历在线会话（排除 self、`Player == null`），`IsFriend(otherName, selfName)` 命中 → `SendFriendListAsync(other, dir, GetFriends(otherName))`。
2. `SendFriendListAsync` 组包：在线好友从会话实时取 Lv/Job/GrowType/频道；**离线好友按名字查 DB character 记录取真实值**（`GetByName`，`delete_flag=0`，查不到才回退默认值）→ self 的 entry 自动带最新值。
3. 重推**不误刷绿/灰图标**：图标由场景实体驱动（§1.2 第 3 点），与列表节点状态位无关。
4. **无新依赖**：全部复用 `SendFriendListAsync`/`GetOnlineSessions`/`GetPlayerName`/`IsFriend`，不向底层纯逻辑服务注入目录引用。

**触发点（升级/转职判定收敛）**：升级判定统一收敛在 `CharacterExperienceService`（`result.LeveledUp`，`Grant`/`GrantToLevel`）。各 handler 在经验结算后判 `LeveledUp` 再调用。

### 4.8 角色删除 / 更名响应（生命周期 hook）

**触发场景**：关系键是**角色名**，角色被删除（名字不再存在）或更名（名字改变）都会让旧键悬空，必须同步清理/迁移表项并刷新相关好友的面板。

**删除角色**（挂载在 `CharacterSelectHandler` DELETE_CHARACTER `SoftDelete` 成功后，best-effort，失败只记日志不影响删除 ACK）：
- `HandleCharacterDeletedAsync(name, dir)`：
  1. **owner 方向**：内存图移除 `name` 键（X 加的所有好友一并消失）。
  2. **friend 方向**：所有把 X 加为好友的 owner 的列表移除 X。
  3. **表**：`DELETE WHERE owner_name=X OR friend_name=X`（单条原子）。
  4. **通知**：只通知 `friend_name=X` 的在线会话（单向语义——X 加的人其面板不显示 X，无需通知）。

**更名角色**（`HandleCharacterRenamedAsync(oldName, newName, dir)`）：
- **owner 方向**：X 的整条好友边迁移键到 Y（Y 已有出边时**并集合并**）。
- **friend 方向**：所有把 X 加为好友的 owner 的列表把 X 换成 Y。
- **表**：两方向 `UPDATE`（owner_name、friend_name）放在**一个事务**里提交，避免"owner 已换名但 friend 未换"的半更新。
- **通知**：与删除相同（向受影响 owner 推送）。

**通知机制（删除/更名共用 `NotifyFriendNameRemovedAsync`）**：对受影响 owner 的在线会话先发 `0x0111 subcmd=2` 删旧节点，再 `SendFriendListAsync` 全量刷新。依据 §7.3：列表节点以名字为键、客户端 `0x14DEF10` 从 RB 树真正删节点，**subcmd=0 全量刷新不清陈旧节点**——只全量会导致被删/被改名角色残留在面板。

**设计要点**：
- **受影响 owner 列表在变更前快照**：变更后 `IsFriend(owner, oldName)` 恒为 false，无法现算；锁内先收集再变更。
- **更名无入口**：86JP 服务端未实现改名卡（`USE_RENAME_CARD 0x01FE` 枚举存在但无 handler），`HandleCharacterRenamedAsync` 为**预留能力**，未来改名功能接入时调用。

## 6. 开发细则（易错点）

### 6.1 单向门控方向（最高频错误）

推送条件一律是 **`IsFriend(观察者, self)`**（谁把 self 加为好友），**不是** `IsFriend(self, 观察者)`。

```csharp
// ✅ 正确：s 的面板显示 self
if (IsFriend(otherName, selfName)) { ... 推 self 的 USERINFO/0x0112 给 s ... }
// ❌ 错误：会变成"self 的面板显示 s"才推，方向反了
```

方向2（self 看好友绿）才是 `IsFriend(selfName, otherName)`。

### 6.2 同频道 vs 跨频道

- 实体（`0x0002`/`0x0006`）：**仅同频道**推。频道由监听端口映射：`10011→ch.11`、`10161→ch.100`、`10200→ch.200`（`GameNetworkConfig.ResolveGameChannel`）。
- 聊天通知（`0x0112`）：**跨频道也推**（无实体，仅按好友关系门控）。

### 6.3 ADD 与 DELETE body 不同构（血泪坑）

- ADD：`[u16 targetUserID][u8 operation][u32 nameLen][name]`
- DELETE：`[u8 operation][u32 targetCharId][name 到尾]`（无长度前缀）

曾按 ADD 格式解析 DELETE → nameLen 读到垃圾、name 空 → 误回 0x15 → 客户端弹"列表不存在该角色"。**改格式必须实测抓包确认，别靠猜。**

### 6.4 "对方不在好友名单中"是客户端本地检查

客户端 `sub_14DDD20` → `0x14DCAF0` 查**本地**好友树，未命中直接弹字符串 `0x18E` 且**根本不会发包**。所以正常 UI 下删非好友时文案由客户端自己弹，服务端 not-exists 分支（回 `[0x00, 0x05]`，0x05 未注册 → 客户端静默）只是状态不同步的防御回包。

### 6.5 成功 ACK 必须 13B

统一响应分派把 flag 后 12B 交给 `0xD13F30`。发不足 13B → 静默 ret → friend_manager 不激活。ADD/DELETE 成功 ACK 都发 `[0x01][0x1BC6][10][2]`（B-C=8>6 → flag=1）。

### 6.6 列表刷新三通道协同

- **subcmd=0 ×2**：建节点 + 置显示。不清陈旧节点。
- **subcmd=2**：真删节点。删除好友**必须先 subcmd=2** 再 subcmd=0 全量刷新。
- 空好友列表：subcmd=2 删完节点后 count=0，`SendFriendListAsync` 直接 return（面板已空，无需再刷）。

### 6.7 并发与幂等

- 所有图操作在 `lock(Sync)` 内，`RemoveFriendship` 幂等；校验后并发移除 → race 分支回 `[0x00, 0x05]`。
- Add 幂等：`RecordFriendship` 已存在时不重复写盘。

### 6.8 空值/异常防护

所有推送方法：self 无名 / 目标名空 → 直接 return；try/catch 包裹，失败仅日志不中断主流程。回城路径 `_sessions`/`_svc.Sessions` 均做 null 检查（部分 handler 在自测/单例模式下 Sessions 可为 null）。

## 7. 信令权威来源（客户端逆向证据）

> 全部结论来自客户端二进制直读反汇编（capstone / 内存快照） + 实机对照双重实锤。
> **权威优先级**：客户端二进制直读反汇编 > 实机行为（面板/弹窗/日志对齐） > 服务端 DispatchTable 注册 > 协议惯例 > 旧 `df_game_r` 反编译（仅历史参考，大量 CMD ID 在客户端被复用重定向，可信度最低）。

### 7.1 客户端唯一数据源

- 反汇编工具链细节（内存快照 `RE/DNF_mem_dump.bin`、capstone 用法、`DNF_unpacked_dump.exe` 不可用原因）见 RE 存档，本节只给出结论。

### 7.2 命令/通知通道与枚举名错位（先看）

**不要看枚举名判断 CMD 归属！** 旧 `df_game_r` 的枚举名与客户端实际绑定**大概率错位**。判断依据按优先级：服务端注册表 `d[ID]=Handler` 函数名 → 客户端日志方向标记 → 实机行为 → 反汇编 handler。

| 通道 | 方向 | 服务端绑定 / 行为 | 旧枚举名（仅供参考，已错位） |
|---|---|---|---|
| `0x0122` (290) | C→S REQUEST + S→C ACK | `HandleAddUnitedServerFriend`（按名字加跨服好友） | RESPONSE_ADD_PVP_BUDDY（**名字错位**） |
| `0x0123` (291) | C→S REQUEST + S→C ACK | `HandleDeleteUnitedServerFriend`（删好友） | REMOVE_PVP_BUDDY |
| `0x0124` (292) | S→C PUSH × cmd=1 | handler `0xD2D6D0`：解析好友列表 + update + ui_refresh | PVP_BUDDY_CONN_LIST |
| NOTI `0x010F` (271) | S→C | **no-op**：handler `0x162B910` = 空函数（只 ret），推送即黑洞 | PVP_BUDDY_CONN_LIST NOTI |
| NOTI `0x010D` (269) | S→C | **禁止**：触发「决斗好友邀请」弹窗 | PVP_BUDDY_IN |

**通道选择（DNF 协议惯例）**：
- **ACK 响应 CMD 包**（`cmd=1`）：S→C 对 C→S 请求的直接回包，**必须复用请求 CMD ID = header.type**（如请求 0x0122 → ACK 也 0x0122）。
- **主动推送**：CMD 包用专用 PUSH ID（如列表推送 0x0111）；NOTI 推送（`cmd=0`）大量 handler = no-op，**发前必须先确认目标 type 的 handler 非空**。
- success_flag（ACK body[0]）：`0x00`=失败 → dispatcher 查表弹 errorCode；非 0=成功 → dispatcher 把剩余 body 传给 CMD handler。

### 7.3 0x0111 好友列表（subcmd 表，0xD0DBB0 先 parse_int32 → switch）

| subcmd | handler | 作用 | body 格式 |
|--------|---------|------|-----------|
| 0 | `0x14E2900` | 好友列表刷新（面板显示） | `[0][count][N × entry(18B+nameLen)]` |
| 1 | `0x14E0920` | 列表装载（同调 `0x14E0730`） | `[1][count][N × entry(18B+nameLen)]` |
| 2 | `0x14DEF10` | 清 `node+0x5D`；三标志(+0x5D/5E/5F)全 0 → `0x14DD2C0` **真删 RB 树节点**（unlink+rebalance+count--） | `[2:u32][count:u32][N × (sR:u8, nameLen:u32, name)]` |
| 3 | `0x14DF7F0` | 跨服在线刷新（双分支：A 命中只写字段 / B 新建节点） | `[3:u32][count:u32][N × (sR, ch:u16, nameLen, name, Lv, Job:u32, GrowType, Y, Z:u32)]` |
| 4 | `0x14DFB00` | 官方「删+重建刷新」 | — |

> **entry 格式（权威，18B+nameLen，0x14DCF90 全字节消费）**：
> `[sR:u8][ch:u16][nameLen:u32][name][Lv:u8][Job:u32][GrowType:u8][Y:u8=0][Z:u32=0]`
> 字段 Y/Z **无任何消费方**（已确认），生产固定 0/0，仅作占位维持 18B 对齐。
> ⚠️ **entry ≠ 23B+nameLen**：count>1 时每多 5B → 后续 entry 起点前移 5×i 全错位。

**name wire 格式**（`0x2092000`）：`u32 nameLen(LE) + nameLen 字节`；`nameLen==0` 或 `≥0x100` → 只消费 4B 前缀、name 用 fallback 串（0x2d05c36），解析继续。

**subcmd=0 装载双路径**（`0x14E0730`，解释"连发两遍"）：
- 路径1（命中已有节点）：`mov byte [node+0x5D], 1` → 设在线 → **绿**
- 路径2（新节点）：构造临时节点 → RB 树插入，新节点 `+0x5D` 默认 0 → **灰**
- 推论：首见走路径2（灰），重发走路径1（绿）→ **必须连发两遍 subcmd=0**（第1遍建节点、第2遍置显示）。

### 7.4 0x0122/0x0123 统一响应分派（0xD13F30 精确行为）

上层 dispatcher 先消费 `body[0]=success_flag`：`0x00`→直接按 `body[1]` 弹 errorCode（**不调 0xD13F30**）；非 0→剩余 12B 传 `0xD13F30`（parse_int32 × 3，无字符串）。

**0xD13F30 分支逻辑**：
- 字段A 有效范围 `[0x1BC6..0x1BF5] ∪ [0x1C15..0x1C19]`，超界静默 ret
- `diff = B − C`：`≤0`→静默 ret；`[1..6]`→show_chat_message（string 0x11202 子索引 diff−1，不设 flag）；`>6`→string 0x11201 + `mov byte [friend_mgr+0xB0165], 1` 设 flag
- **生产默认 A=0x1BC6, B=10, C=2（diff=8>6 → 设 flag 路径）**
- 成功路径聊天消息因 string 0x11201/0x11202 本地化缺失而 UI 不可见，属正常。

### 7.5 errorCode 表（ADD/DELETE 失败 ACK `[0x00, errorCode]`）

| errorCode | 弹窗文案 | 触发场景 |
|---|---|---|
| `0x04` | 好友已满，无法继续添加好友 | `GetFriends(selfName).Count >= 100` 且非好友（客户端上限 100：`0x14E0380` L273 `cmp dword ptr [esi+4], 0x64` 实锤） |
| `0x07` | 在普通频道，只能添加相同大区的玩家为好友 | 单区环境恒匹配，**不实现** |
| `0x15` | 该角色不存在 | 目标名空 / `_characterRepository.GetByName()==null` |
| `0x01` / `0x0D` / `0x85` / 其他 | 无文案 → **静默不弹** | 不能加自己等；删除非好友的 0x05 也走此档 |

### 7.6 客户端本地删除检查（"对方不在好友名单中"来源）

`sub_14DDD20` → `0x14DCAF0` 查**本地**好友树，未命中直接弹字符串 `0x18E`（0xA2CB310）且**根本不发包**。所以该文案是客户端本地行为，服务端无需（也无法）复刻；服务端 not-exists 分支只回 `[0x00, 0x05]` 作防御（0x05 未注册 → 静默）。

### 7.7 UserState 逆向结论

- **USERINFO(0x0002) body 第 6 字节（下标 5）= UserState**（服务端 `UserInfoSubtype0Builder.BuildRemainingBytes` 布局实锤）。
- **落点** = 角色/好友实体偏移 **+0x18**（两个实例：`@0A5C100B` / `@42150091`），原样存储。
- **客户端无枚举校验**：GREEN:SEQ 推 0..7，实体 +0x18 全部原样存储（0x00~0xFF 全接受）。**有语义的枚举由服务端定义**：0x00=城镇/在线、0x01=副本、0x02=PvP。
- **图标判断 = 单点布尔比较** `UserState==1 ? 繁忙 : 在线`（非多值枚举 switch）。0x02=PvP、未定义值 3/12 等 `!=1` 一律显示"在线"。
- **用户实测**：UserState 0→1 变繁忙，2/3/12 显示在线。
- **边界**：分派器 `0x11856F0` 受 VM 保护（body 解析在字节码内，静态不可翻）；`cmp byte [reg+0x18],1` 全 dump 零命中（UI 从好友条目/UI 节点读，非实体 +0x18）；`DebugActiveProcess` attach 已登录客户端触发反调试自毁（游戏闪退）→ **动态验证一律纯 ReadProcessMemory，不可 attach**。行为级结论确凿，指令级还原放弃。

### 7.9 旧服务端（df_game_r）对照 —— 与 united-server 的差异

86JP 客户端「添加好友」按钮绑定 **United Server Friend（0x0122）**，**不是**旧普通好友系统（CMD 63/64）：

| 维度 | 旧 Friend（df_game_r） | united-server（0x0122/0x0123） |
|---|---|---|
| C→S body | `[nameLen:i32][name]` | `[targetUserID:u16][op:u8][nameLen:u32][name]`（ADD）/ `[op:u8][charId:u32][name 到尾]`（DELETE） |
| ACK | CMD 63 成功 ACK handler **no-op**（0x162B910）；64 成功 `[0x01][nameLen][name]` 但 name 被忽略 | 13B `[0x01][3×int32]`（0xD13F30 真解析） |
| 失败 ACK | `[0x00][errCode]`（统一，两系统一致） | 同左 |
| 列表推送 | NOTI 54/55（6B）+ NOTI 56 no-op + type=0x33/0x4C/0x66（仅客户端有，服务端无 put 函数） | 0x0111 subcmd=0（18B+nameLen entry） |
| 跨服链路 | GameServer ↔ MonitorServer / CommunityServer | 单机模拟器在进程内内存好友表直接处理，无跨服 |
| 判断 CMD 归属 | 枚举名不可信（错位） | 看服务端 `d[ID]=Handler` 注册 |

**教训**：旧系统的 ACK/列表格式**不能**套用到 united-server（曾照搬 ADD 格式解析 DELETE 而踩坑）。

### 7.10 已证伪 / 禁止事项（防回溯）

| 项 | 结论 |
|----|------|
| type=0x0124(292) 是好友列表显示通道 | ❌ 面板显示走 0x0111；0x0124 是 PvP 连接列表，未实现 |
| NOTI 0x010F(271) 推好友列表 | ❌ handler no-op（0x162B910），推送即黑洞 |
| NOTI 0x010D(269) | ❌ 触发「决斗好友邀请」弹窗，**禁止** |
| entry = 23B+nameLen | ❌ count>1 全错位；真实 = 18B+nameLen |
| ACK = 12B（无 success_flag 前缀） | ❌ dispatcher 误消费字段A 低字节 → 静默失败；**必须 13B** |
| 0x0112 可让在线图标变绿 | ❌ 它只写 `node+0x5E=(oF!=0)`（黑名单位），`oF≠0` 会**进黑名单** |
| subcmd=2 单包置灰 | ❌ 三标志全 0 时 `0x14DD2C0` **真删节点**（好友消失）；置灰必须「删+重建」 |
| UserState 是多值枚举 switch | ❌ 单点布尔 `==1 ? 繁忙 : 在线` |

**踩坑记录**：

- `push 0x18E`/`push 0x18D` 不是字符串引用，是 **NOTI 类型注册**（type 0x18E→handler 0xCC6970、0x18D→handler 0xCC6A70）。
- 注册表 handler 是「NOTI 状态提示回调」（type 2→0xCC62C0、type 6→0xCC5C60 只做日志/UI 提示，case 值 7/0x41、2/0x13/0x15 与 UserState 0/1/2 不对应），**不是** USERINFO/USER_LEAVE 实体解析主路径——实体解析在另一条链（VM 内，静态不可翻）。
- capstone 扫描要认准函数边界（`mov esp,ebp; pop ebp; ret` 结束），否则跨函数合并 parse 计数。
